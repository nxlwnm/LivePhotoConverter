# 技术开发须知（强制规范）

> 本文是项目开发的约定基线，所有参与者（含 AI 助手）在编写代码前必须遵守。
> 与本文冲突的做法需先修订本文，再实施。
> 最后更新：2026-10-12

## 1. 语言、版本与环境

- **N1.1** Python 版本：`>=3.13`，`pyproject.toml` 中 `requires-python = ">=3.13"`。
- **N1.2** 环境管理优先使用 **uv**；`venv` 作为无 uv 场景的备选路径，两者都必须能跑通（见 `40`）。
- **N1.3** 禁止把依赖直接安装到系统 Python；所有命令通过 `uv run` 或激活 `.venv` 后执行。
- **N1.4** 虚拟环境目录统一为仓库根 `.venv`，且必须加入 `.gitignore`。
- **N1.5** 所有脚本必须能在 Windows(PowerShell) 与 macOS(zsh) 上执行，禁止使用平台独占 shell 语法。
- **N1.6 技术栈边界**：项目主体为 Python。非 Python 组件（如 iOS 宿主 App）只允许在设备接入层以**单点**形式引入，必须隔离在独立目录与独立构建流程中，不得出现在核心链路。
- **N1.7 引入非 Python 组件的准入条件**（四者缺一不可）：① 已归档"纯 Python 通道均不可行"的实测证据；② 经过单独评审；③ 在 `Doc/40` 登记其构建与运行方式；④ 其余模块仍可在纯 Python 环境下完整运行。

## 2. 依赖管理规范（强约束）

- **N2.1** 依赖的**单一真源**是 `pyproject.toml`，可复现锁定文件是 `uv.lock`；`requirements.txt` / `requirements-dev.txt` 是由 uv 导出的**产物**，禁止手改。
- **N2.2 新增依赖的完整流程**（缺一不可）：
  1. `uv add <pkg>`（或 `uv add --dev <pkg>` 加入开发依赖组）；
  2. 确认 `uv.lock` 已更新并提交；
  3. `uv export` 重新生成 `requirements.txt` 与 `requirements-dev.txt`；
  4. 在 `40-环境搭建与依赖管理.md` 的「依赖清单」表中登记：包名、版本约束、用途、引入里程碑、是否跨平台可用；
  5. 若该依赖在某一平台不可用或需要额外系统组件，必须在表中标注并同步更新 setup 脚本的检测项；
  6. 提交时在同一改动中说明引入理由。
- **N2.3** 依赖准入标准：优先标准库 → 成熟活跃库 → 其余。引入前需回答：是否必须用第三方？是否跨平台？是否维护活跃？是否显著增加安装体积？
- **N2.4** 禁止引入重量级依赖（深度学习/大型 CV 框架等）而未经过评审。
- **N2.5** 外部二进制工具（ffmpeg/ffprobe、exiftool、hdc、adb 等）**同样属于依赖**，必须在 `40` 的依赖清单中登记最低版本、获取方式、平台支持情况。
- **N2.6** 禁止把任何二进制可执行文件提交进版本库。

## 3. 目录使用规范

- **N3.1** `Doc/`：只放规范、调研、报告；文档按 `编号-名称.md` 命名，编号递增便于排序。证据（工具输出、元数据快照、样本登记表与指纹）统一放 `Doc/evidence/`，按平台分子目录。
- **N3.2** `Src/`：只放源码与测试，不放样本、日志、临时产物。
- **N3.3** `Tmp/`：运行期临时文件，必须以 `run_id` 分子目录（`Tmp/<run_id>/...`），完成后按策略清理；**不入版本库**。
- **N3.4** `Log/`：运行日志写入此处，按天轮转，保留策略默认 14 天；**不入版本库**。
- **N3.5** 样本文件放 `Tmp/samples/`（不入版本库）；样本登记表与指纹（hash/元数据摘要）放 `Doc/evidence/`，随代码入库。
- **N3.6** 空目录需放置 `.gitkeep` 才能入库。
- **N3.7** 目录与包名一旦确定，禁止变更大小写（Windows 大小写不敏感而 Git 敏感）。
- **N3.8** `scripts/`：只放环境初始化与工程辅助脚本（setup、环境检查、清理），不放业务逻辑；每个脚本必须同时提供 `.ps1` 与 `.sh` 版本且行为一致；不参与打包。

## 4. 编码规范

- **N4.1** 源文件统一 **UTF-8 无 BOM**；换行统一 LF，通过 `.gitattributes` 固化。
- **N4.2** 行长上限 120；使用 ruff 做格式（等同 black 风格）与 lint，配置统一在 `pyproject.toml`。
- **N4.3** 公共函数/方法必须写类型注解；项目启用 mypy（渐进式，新增代码必须过检）。
- **N4.4** 命名：模块/包 `snake_case`，类 `PascalCase`，函数/变量 `snake_case`，常量 `UPPER_SNAKE_CASE`；平台标识统一小写无分隔符（如 `harmonyos`、`originos`）。
- **N4.5** 注释：不对能自解释的代码写注释；文档字符串（docstring）精简，只写"做什么"与关键约束，public/internal API 必须有，私有实现非必要不加。
- **N4.6** 禁止在代码中硬编码绝对路径、设备序列号、样本名；统一走配置或参数。
- **N4.7** 所有文件系统路径操作使用 `pathlib`，禁止字符串拼接路径。
- **N4.8** 子进程调用必须通过 `media/` 封装层，禁止业务代码直接拼接命令行，且必须处理超时与非零退出码。

## 5. 日志规范

- **N5.1** 使用标准库 `logging`，统一通过 `utils/logging_setup.py` 初始化，禁止各模块自行 `basicConfig`。
- **N5.2** 日志同时输出到控制台与 `Log/<date>.log`，格式统一：`时间 级别 模块名 消息`。
- **N5.3** 级别约定：DEBUG 用于解析细节与工具原始输出；INFO 用于流程节点；WARNING 用于降级/可疑；ERROR 用于单文件失败；CRITICAL 用于环境不可用。
- **N5.4** 长任务按 `run_id` 串联，关键节点打印 `run_id`，便于回溯。
- **N5.5** 日志脱敏：禁止打印设备序列号、绝对路径中的用户名、GPS 坐标等敏感信息；必要时打码。
- **N5.6** 禁止把二进制内容、整段工具输出无节制写入日志（大输出写入 `Tmp/<run_id>/`）。

## 6. 错误与结果规范

- **N6.1** 定义统一异常基类与错误码（如 `E_INPUT_*` / `E_PARSE_*` / `E_TRANSFORM_*` / `E_WRITE_*` / `E_DEVICE_*` / `E_ENV_*`），错误码集中维护并在文档中登记。
- **N6.2** 批量转换中单条失败不得中断整批：捕获、记录、继续，最终汇总报告。
- **N6.3** 每条转换结果必须包含：输入标识、输出路径、状态、耗时、降级项、错误码（如有）。
- **N6.4** 禁止静默降级：任何自动裁剪/转码/补值都必须体现在结果报告与日志中。
- **N6.5** 环境缺失（外部工具未安装、版本不符）应在启动阶段通过 `doctor` 明确暴露，而不是运行中途崩溃。

## 7. 测试规范

- **N7.1** 使用 pytest；目录 `Src/tests/{unit,integration,regression}`。
- **N7.2** 单测不得依赖真机与外部网络；集成测试可使用外部工具（ffmpeg/exiftool）但需可跳过。
- **N7.3** 回归测试依赖样本集；样本缺失时自动跳过（`pytest.mark.skipif`），不得因缺样本而失败。
- **N7.4** 每个平台适配器至少覆盖：正常样本、缺静态帧、缺视频、超长视频、异常方向、损坏文件。
- **N7.5** 修改解析器或生成器后必须复跑全量回归并记录结果。

## 8. 版本控制与提交规范

- **N8.1** 使用 Conventional Commits：`feat:` / `fix:` / `docs:` / `refactor:` / `test:` / `chore:`，建议带 scope（如 `feat(ios):`、`fix(harmonyos):`）。一次提交只做一件事。
- **N8.2** 禁止提交：`.venv`、`Tmp/*`、`Log/*`、`Tmp/samples/**`、样本原文件、密钥、设备序列号、二进制工具、大型媒体文件。
- **N8.3** 涉及依赖、目录结构、外部工具的改动，必须在同一次提交中同步更新 `Doc/40` 与相关文档。
- **N8.4** 版本号遵循 SemVer；`0.x` 阶段允许不兼容变更，但需在文档中说明；里程碑达成时打 tag（`v0.1.0` 形式）。
- **N8.5** 提交前必须本地通过 `ruff` 与 `pytest`；推送前必须确认 `git status` 干净、无未跟踪的大文件。
- **N8.6** `.gitignore` 与 `.gitattributes` 必须在首次提交时就位：换行统一 LF；`uv.lock`、`requirements*.txt`、`Doc/evidence/` 必须入库，`.venv`、`Tmp/*`、`Log/*`、样本必须排除。
- **N8.7** 分支策略：默认分支 `main` 保持可用；日常开发用短生命周期分支（`feat/xxx`、`fix/xxx`），合并前自查，禁止对 `main` 强制推送。
- **N8.8** 远端与 GitHub：
  - 远端命名 `origin`；仓库在验证阶段建议先设为**私有**，公开前做一次敏感信息扫描（路径中的用户名、设备序列号、样本与私钥）；
  - 公开仓库需包含 `README.md` 与 `LICENSE`；本项目协议已选定 **MIT**；
  - 大文件不入库，不使用 Git LFS（样本一律留本地 `Tmp/samples/`）；仓库体积控制在常规量级，单文件不得超过 GitHub 的 100MB 限制。
- **N8.9** 禁止在提交信息、代码注释与文档中写入个人绝对路径、设备标识与任何凭据；日志与报告中的路径需相对化（同 N5.5）。

## 9. 文档规范

- **N9.1** 先文档后代码：新增平台、新增依赖、变更架构，先更新 `Doc` 再动代码。
- **N9.2** 文档中的格式结论必须附**可复现证据**（使用的命令、工具版本、样本指纹），证据归档到 `Doc/evidence/`。
- **N9.3** 调研结论需区分三态：`已验证` / `推测（待验证）` / `不适用`，禁止把推测写成结论。
- **N9.4** 文档中禁止写入个人绝对路径、设备序列号、隐私信息。

## 10. 安全与隐私

- **N10.1** 样本默认视为敏感数据：不入版本库，分享前脱敏（裁剪人脸/清除 GPS 或明确授权）。
- **N10.2** 日志与报告中的路径统一相对化，避免泄露用户名。
- **N10.3** 禁止在代码中写入任何账号、密钥、个人设备标识。
