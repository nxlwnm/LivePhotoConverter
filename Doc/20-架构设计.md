# 架构设计

> 状态：草案，待评审确认（与 `10-需求评估与风险分析.md` 的 Q 清单一并确认）
> 最后更新：2026-10-12

## 1. 设计原则

| # | 原则 | 说明 |
| --- | --- | --- |
| P1 | 平台差异隔离在适配层 | 核心编排不感知任何平台专有格式，平台知识只存在于 Extractor / Writer / Profile 中 |
| P2 | 以 IR 为唯一中转 | 转换路径统一为 `源格式 → IR → 目标格式`，避免 n×n 直接耦合 |
| P3 | 可验证优先 | 每个环节可独立验证（解析可回读、生成可校验、端到端有真机判据） |
| P4 | 外部工具封装调用 | ffmpeg/ffprobe/exiftool 等统一走封装层，禁止业务代码直接拼命令行 |
| P5 | 显式降级，不静默失败 | 任何不满足目标平台约束的情况都要在结果报告中显式记录 |
| P6 | 设备接入可替换 | 真机通道与本地文件通道实现同一接口，任一通道不可用时可切换 |
| P7 | 依赖最小化与准入 | 每新增一个依赖需登记用途并在文档中说明理由（见 `30`） |

## 2. 分层架构

```
┌──────────────────────────────────────────────────────────┐
│ L6 接口层        CLI (convert / probe / verify / doctor)  │
├──────────────────────────────────────────────────────────┤
│ L5 编排层        Converter 组合 · Pipeline · 批量 · 报告  │
├──────────────────────────────────────────────────────────┤
│ L4 生成层        Writer: ios / harmonyos / android / ...  │
│ L2 解析层        Extractor: ios / harmonyos / ...         │
├──────────────────────────────────────────────────────────┤
│ L3 中间层        IR 模型 · 兼容化变换(Transform) · 校验   │
├──────────────────────────────────────────────────────────┤
│ L1 设备接入层    DeviceBridge: hdc / adb / 本地目录 / 手动 │
├──────────────────────────────────────────────────────────┤
│ L0 支撑层        媒体工具封装 · 日志 · 配置 · 错误码       │
└──────────────────────────────────────────────────────────┘
```

各层职责：

| 层 | 职责 | 关键约束 |
| --- | --- | --- |
| L6 接口层 | 命令行与库 API；参数解析、输出格式（人读/JSON） | 不含业务逻辑 |
| L5 编排层 | 依据 `源平台 → 目标平台` 从注册表取 Extractor/Writer 组合；执行 Transform；批量、并发与断点续做；生成报告 | 不感知具体平台 |
| L4/L2 适配层 | 平台格式的解析与生成，含平台约束描述（Profile） | 只允许依赖 IR 与 L0，不允许跨平台互相依赖 |
| L3 中间层 | IR 数据模型、IR 校验、按目标 Profile 做兼容化变换（裁剪时长/转码/补元数据） | IR 不绑定任何平台私有概念 |
| L1 设备接入层 | 从设备取源文件、向设备投递产物；连通性自检 | 与平台格式无关，可独立替换实现。鸿蒙真机（hdc）为首选输入通道；iOS 相册回灌为必需输出通道 |
| L0 支撑层 | ffmpeg/ffprobe/exiftool/heif 等封装；日志；配置；错误码 | 统一入口，便于替换与测试 |

## 3. 中间模型 IR（草案）

IR 是平台无关的最小完备描述，字段随 M2 调研结果迭代。

```text
LivePhoto (IR)
├── still               静态帧
│   ├── data / path     原始字节或文件路径（二选一，优先路径以支持大文件）
│   ├── mime            image/jpeg | image/heic
│   ├── width / height
│   ├── orientation     EXIF 方向
│   ├── hdr            HDR 信息（GainMap / 色彩空间），必保项，不可用时需记录降级
│   ├── depth          景深/人像深度数据（探索项，可为空）
│   └── raw_meta        保留的完整原始元数据（用于无损搬运，未识别字段不丢）
├── video               动态视频
│   ├── path
│   ├── container       mp4 | mov
│   ├── codec           h264 | hevc | ...
│   ├── width / height / fps / rotation
│   ├── duration_ms
│   └── raw_meta
├── pairing             配对信息
│   ├── still_time_ms   视频轴上静止帧所在时刻（无则默认首帧）
│   └── content_id      关联标识（可选；由 Writer 生成亦可）
├── meta                描述信息
│   ├── capture_time / timezone / gps
│   ├── device / source_platform
│   └── extras          平台特有、暂未归一的信息（字典，避免提前抽象）
└── diagnostics         解析期产生的问题记录（缺失项、可疑项、已做的修补）
```

设计要点：

- **`raw_meta` 与 `extras` 是关键**：格式调研未完成时，不要为了"模型干净"丢掉未知字段，否则后续无法补救。
- **`diagnostics` 随 IR 传递**：解析阶段发现的问题必须带到最终报告，而不是只打日志。
- **IR 可序列化**（JSON 摘要，不含二进制），便于回归测试与问题复现。

### 3.1 为什么不以 iOS 文件格式直接作为中转

| 维度 | iOS 文件中转 | IR 中转 |
| --- | --- | --- |
| 实现量 | n 个解析器 + n 个生成器（同 IR） | 相同 |
| 耦合 | 所有平台都必须理解 iOS 私有概念（关联标识、静止帧时刻标记、iOS 编码约束） | 平台只与 IR 交互 |
| 信息损耗 | 多次中转反复按 iOS 约束裁剪，不可复原 | 只在最后一步按目标 Profile 裁剪 |
| 未来扩展（如 Android↔鸿蒙） | 需要绕道 iOS 语义，语义不自然 | 直接两端组合 |
| 可测试性 | 需要 iOS 语义样本 | 可构造纯 IR 用例 |

结论：IR 的语义以「静态帧 + 动态视频 + 配对关系 + 描述元数据」为核心，这一模型与 iOS Live Photo 天然高度重合，因此 iOS 序列化几乎是"直出"，不会带来额外成本，但换来了解耦与可扩展性。

## 4. Converter 组合机制

```text
Converter(source, target) = Extractor(source) → [Transform...] → Writer(target)
```

- **注册表**：平台能力以 `platform + role(extract/write) + version` 注册，编排层按 (source, target) 自动组合，天然支持 n×n 扩展；
- **能力协商**：每个目标平台提供 `Profile`（约束集合：最大时长、允许编码/容器、分辨率上限、必需元数据），Transform 依据 Profile 做兼容化；
- **降级策略可配置**：截断 / 变速 / 转码 / 拒绝，默认策略与可选策略由 `30` 与 `50` 明确；
- **失败隔离**：批量转换中单张失败不影响其他，全部结果汇总为报告（含失败原因与错误码）。

### 4.1 转换流程（Harmony → iOS 示例）

1. `DeviceBridge(鸿蒙)` 拉取源文件到本地工作区（`Tmp/<run_id>/`）；
2. `Extractor(harmonyos)` 解析为 IR，记录 `diagnostics`；
3. `IR 校验`：静态帧与视频是否齐全、时长/分辨率是否可读；
4. `Transform(ios_profile)`：必要时裁剪时长、转码、补方向/时间元数据、生成关联标识；
5. `Writer(ios)` 生成静态图 + 配对视频 + 关联元数据；
6. `Verify`：回读产物，校验配对标识一致、时长/编码/分辨率符合 Profile、静止帧时刻正确；
7. `DeviceBridge(iOS)` 投递产物到相册（实现优先纯 Python + 命令行工具；纯 Python 通道均不可行时，才启用单点非 Python 实现，见 `30` N1.6/N1.7）；
8. 真机确认（长按播放、静止帧一致）并归档证据到 `Doc/evidence/`；
9. 写入 `Log/` 与转换报告。

## 5. 目录结构（Src 详细）

建议采用 src-layout，`pyproject.toml` 置于仓库根并指向 `Src`。

```
Src/
├── livephoto/                  # 主包（CLI 名建议 lpconv）
│   ├── cli/                    # L6：命令实现 convert/probe/verify/doctor
│   ├── core/                   # L3/L5：IR 模型、注册表、Pipeline、报告、错误码、配置
│   ├── platforms/
│   │   ├── common/             # Extractor/Writer/Profile 抽象基类
│   │   ├── ios/                # extractor.py / writer.py / profile.py
│   │   ├── harmonyos/
│   │   ├── android/            # 后续
│   │   └── originos/           # 后续
│   ├── device/                 # L1：hdc / adb / 本地目录 等 Bridge 实现
│   ├── media/                  # L0：ffmpeg / ffprobe / exiftool / heif 封装
│   └── utils/                  # 日志、文件、校验等通用工具
└── tests/
    ├── unit/
    ├── integration/
    └── regression/             # 样本集回归（依赖外部样本，缺省时自动跳过）
```

顶层目录职责与取舍：

| 目录 | 用途 | 规范 |
| --- | --- | --- |
| `Doc` | 规范、调研、验证报告 | 编号前缀命名，改动需与代码同步 |
| `Doc/evidence/` | 调研与验证证据、样本登记表与指纹 | 随代码入库，不含样本本体 |
| `Src` | 全部源码与测试 | 不含设备样本、不含日志 |
| `scripts/` | 环境初始化与工程辅助脚本 | 必须同时提供 `.ps1` 与 `.sh` 且行为一致；不参与打包 |
| `Tmp` | 运行期临时文件，按 `run_id` 分子目录 | 不入版本库，有清理策略 |
| `Tmp/samples/` | 样本本体 | 不入版本库，视为敏感数据 |
| `Log` | 运行日志 | 不入版本库，按天轮转 |

> 注意：Windows 文件系统大小写不敏感而 Git 敏感，目录/包名一旦确定不得变更大小写。

## 6. 新增平台接入 Checklist

1. 在 `Doc/60-平台格式调研.md` 补齐该平台条目（容器、关联机制、约束、导出/导入通道、证据）；
2. 新增 `platforms/<name>/profile.py`：声明目标约束；
3. 实现 `extractor.py` / `writer.py`（至少一个方向），注册到注册表；
4. 补充该平台的样本到样本集并登记；
5. 补充单测与回归用例；
6. 更新 `Doc/40` 若引入新的外部工具依赖；
7. 真机验证并归档证据。

## 7. 关键决策记录（ADR 摘要）

| ID | 决策 | 备选方案 | 理由 |
| --- | --- | --- | --- |
| ADR-001 | IR 为唯一中转，iOS 约束固化为 Profile 供兼容化变换使用（已确认） | 以 iOS 文件格式中转 | 实现量相同但耦合更低、可扩展、可测试；iOS Profile 只作用于 Transform，不污染 IR 语义，见 3.1 |
| ADR-002 | 设备接入独立成层 | 内置于 Converter | 鸿蒙导出与 iOS 回灌是高不确定性环节，需可替换与独立验证 |
| ADR-003 | 媒体处理复用命令行工具（ffmpeg/exiftool） | 纯 Python 库 | 编解码与元数据写入成熟度与兼容性优先；统一封装以隔离 |
| ADR-004 | 依赖以 pyproject + uv.lock 为单一真源 | 手写 requirements.txt | 可复现、可锁定、可导出；requirements 作为兼容产物 |
| ADR-005 | 转换结果必须可校验（verify） | 仅转换不校验 | 跨平台格式问题隐蔽，无校验则失败不可观测 |
| ADR-006 | 校验贯穿但真机判据为最终标准 | 仅文件级校验 | 文件"看起来对"不等于相册能识别 |
| ADR-007 | 建议新增 M0 脚手架里程碑并在 M2 设 Go/No-Go | 直接三里程碑 | 提前建立规范与环境，避免返工；高风险项早判定 |
| ADR-008 | 非 Python 组件统一放顶层 `native/` 并在 `README.md` 与 `Doc/40` 标记 | 混入 `Src` 或散落各处 | 使"本项目含非 Python 组件"对外可见，便于评审、构建与维护（见 `30` N1.8） |
| ADR-009 | HDR 纳入必保范围，景深作为探索项（确认不兼容可降级） | 元数据一律尽力而为 | 保真要求已明确；HDR 影响观感，且降级必须对用户可见（见 `10` Q3） |
| ADR-010 | 批量默认失败隔离，并发与断点续做作为设计目标 | 仅串行批量 | 批量为明确需求；任务状态持久化成本可控（见 `30` N6.6） |
