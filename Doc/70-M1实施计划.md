# M1 实施计划（设备环境调试）

> 状态：执行中（2026-10-12 启动）
> 目标：把项目最大的两个不确定性——**鸿蒙侧原始文件导出**与 **iOS 侧相册回灌**——解决掉。
> 本文件是 `50-里程碑计划.md` 中 M1 的展开版，任务编号（A/B/C/D/E）与本文一致。

## 1. 当前环境状态

| 项 | 状态 |
| --- | --- |
| Python 3.13 / uv | 就绪（`.python-version` 固定） |
| hdc 3.2.0f | 已安装并加入用户 PATH |
| 鸿蒙真机 | 已授权，`hdc list targets -v` 显示 USB `Connected` |
| iOS 设备 | Apple Mobile Device Service 运行中；回灌通道**未验证** |
| ffmpeg / ffprobe / exiftool | **未安装**（A 阶段补齐） |
| 样本集 | 未建设（D 阶段） |

## 2. 验收标准（DoD）

1. **鸿蒙侧**：hdc 拉取连续成功 3 次，且拉取文件与设备侧一致（大小一致 + 本地 hash 留档，能证明未被二次转码或剥离）；
2. **iOS 侧（静态图）**：外部静态图导入相册连续成功 3 次，通道可复现；
3. **iOS 侧（动态照片）**：静态图 + 视频对被识别为 Live Photo 至少成功 1 次，长按可播放；
4. **样本集**：不少于 10 组，覆盖矩阵达成，登记表完整（样本本体不入版本库）；
5. **产出**：《M1 设备环境调试报告》，含通道可用性结论、限制与已知问题；所有结论附可复现证据。

> 若第 2、3 项在穷尽纯 Python 通道后仍不可行，按 `30` N1.7 进入"最小 iOS 宿主 App"方案评审，**评审通过前不进入 M2**。

## 3. 任务分解

### 阶段 A：补齐外部工具

- **A1 安装 ffmpeg / ffprobe / exiftool**
  - 做法：执行 `scripts\setup.ps1 -InstallTools`（winget）；winget 源 ID 失效时改为手工安装并把目录加入 PATH。
  - 验收：`lpconv doctor` 中三项由 WARN 转为 OK。
  - 产出：`Doc/40` 外部工具表回填实际版本与最低版本。

### 阶段 B：鸿蒙侧导出通道

- **B1 探测设备上动态照片的存储位置与文件形态**
  - 做法：`hdc shell ls` 依次探查常见媒体目录；用 `find` 定位近期图片；观察动态照片是单文件（内嵌视频）还是图片 + 视频双文件。
  - 验收：明确动态照片在设备上的目录与文件形态，形成"机型 / 系统版本 / 路径 / 形态"记录。
  - 产出：证据归档 `Doc/evidence/harmonyos-storage.md`（命中 `60` 的 H1~H3）。

- **B2 拉取样本并校验原始性**
  - 做法：`hdc file recv <远端路径> <本地目录>`（本地落到 `Tmp/samples/`）；本地计算 hash；与设备侧比对文件大小（设备侧无 `md5sum` 时以大小 + 拉取前后时间戳佐证）。
  - 验收：连续 3 次拉取成功，本地 hash 与大小记录完整，文件可被系统/工具正常识别。
  - 产出：拉取记录（命令、耗时、hash、大小）。

- **B3 记录设备与系统信息**
  - 做法：`hdc shell param get` 读取机型与系统版本（字段名以实测为准）。
  - 验收：机型、系统版本、图库版本明确，纳入机型矩阵。
  - 产出：样本登记表与机型矩阵。

- **B4 兜底通道评估**
  - 做法：若 hdc 拉取受限，评估手动导出（图库分享/USB 传输）作为兜底输入的可行性与其是否被二次转码。
  - 验收：明确 hdc 为主通道，兜底通道可用性有结论。

### 阶段 C：iOS 侧回灌通道（按"先通道、后配对"拆分）

- **C1 静态图通道验证（先解耦通道问题）**
  候选按优先级实测，每条记录结论与证据：
  1. **pymobiledevice3（Python 库，优先）**：与项目技术栈一致，可脚本化；尝试经 AFC 写入相册可扫描的目录，再用 iOS 相册确认可见。
     - 引入该依赖时**完整执行 `30` N2.2 流程**（登记用途、更新锁文件与 requirements、同步文档），顺带补齐 M0 遗留的"依赖流程演练"。
  2. **iTunes 照片同步**：文件夹同步到设备，确认照片是否保留原始件与元数据。
  3. **iCloud for Windows**：上传到 iCloud 照片后观察设备侧结果。
  4. **第三方工具**（iMazing 等）：评估是否可脚本化/批量。
  5. 上述均不可行时，再评估 `30` N1.7 的自建 iOS 宿主 App 方案。
  - 验收：至少一条通道连续 3 次成功（静态图进入相册且元数据正确）。

- **C2 动态照片配对验证（再解耦配对问题）**
  - 做法：用 C1 成功的通道，导入"静态图 + 视频"文件对，观察是否被识别为 Live Photo、长按是否可播放、静止帧是否为源图。
  - 验收：至少 1 次成功；记录配对成立所需的条件（文件命名、目录、元数据）。
  - 产出：证据归档 `Doc/evidence/ios-import.md`（命中 `60` 的 V5、V9）。

### 阶段 D：样本集与证据

- **D1 建设样本集**：不少于 10 组，覆盖横竖屏、不同分辨率、不同时长、HDR / 非 HDR、前置 / 后置。
- **D2 样本登记表**：机型、系统版本、来源、hash、大小、时长、分辨率、方向、HDR、备注；登记表与指纹入 `Doc/evidence/`，样本本体留 `Tmp/samples/`（不入库）。
- **D3 证据归档**：每条结论附命令 + 工具版本 + 输出片段，按 `60` 的三态标记（已验证 / 推测 / 不适用）。

### 阶段 E：报告与收尾

- **E1** 产出《M1 设备环境调试报告》并入 `Doc/`。
- **E2** 回填 `60-平台格式调研.md` 的待验证清单（H1~H10、V1~V11 中本阶段可回答的部分）。
- **E3** 更新 `50` 的 M1 状态与遗留问题，提交推送。

## 4. 执行顺序与依赖

```
A ──> B ──┐
          ├──> D ──> E
A ──> C ──┘
```

- A 是 B、C 的前置（校验元数据与转码需要 ffprobe / exiftool）；
- B 与 C 相互独立，可交叉推进；
- D 依赖 B（样本来源）；E 最后。

## 5. 风险与应对

| 风险 | 应对 |
| --- | --- |
| iOS 回灌通道不可行（R1，最高风险） | 按 C1 优先级逐条实测并归档失败证据；全部不可行才走 N1.7 评审，不静默扩大范围 |
| 鸿蒙侧 hdc 拉取受限（R2） | 记录受限点，启用 B4 兜底通道并标注其为二次转码风险 |
| 样本不足或不具代表（R8） | D1 覆盖矩阵强制达标后再进入 E |
| 引入新依赖导致环境脆弱（R11） | pymobiledevice3 等新依赖必须走 N2.2，且评估跨平台可用性 |
| 隐私（R10） | 样本不入版本库，日志与报告去设备标识与绝对路径（N8.9、N5.5） |

## 6. 纪律约束

- 所有格式结论必须区分 `已验证 / 推测（待验证） / 不适用`，禁止把推测写成结论（N9.3）；
- 文档与证据中禁止出现设备序列号、个人绝对路径与凭据（N8.9）；
- 新增依赖必须完整执行 N2.2 六步；
- 确需引入非 Python 组件时必须按 N1.7 评审、N1.8 标记。
