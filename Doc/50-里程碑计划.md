# 里程碑计划

> 状态：草案。原计划 3 个里程碑，本文建议前置一个 M0，并在 M2 末尾设置 Go/No-Go 判定点。
> 最后更新：2026-10-12

## 1. 里程碑总览

| 编号 | 名称 | 目标一句话 | 主要产出 | 判定方式 |
| --- | --- | --- | --- | --- |
| M0（建议新增） | 工程脚手架与环境 | 让两台机器都能一键跑起来 | 仓库结构、依赖基线、setup 脚本、CLI 骨架、日志与 lint | Windows 与 macOS 各一台全新机器，setup 脚本执行后 `doctor` 全绿 |
| M1 | 设备环境调试 | 打通"拿到源样本"与"送进 iOS 相册"两端 | 鸿蒙导出通道、iOS 回灌通道、样本集与登记表 | 两端各连续成功 3 次，样本集覆盖矩阵达成 |
| M2 | 技术方案探索验证 | 证明 Harmony→iOS 可行并定下参数 | 格式调研结论、参数矩阵、端到端 Spike | **Go/No-Go**：至少 1 组样本在 iOS 真机长按可播放且静止帧正确 |
| M3 | 首个 Converter 实施 | 产品化 Harmony→iOS Converter | CLI（convert/probe/verify/doctor）、批量、回归测试、使用文档 | 样本集通过率达标 + 真机验收通过 |

后续路线（不在本期范围，仅占位）：M4 iOS→HarmonyOS；M5 Android/OriginOS→iOS；M6 任意互转与批量性能优化。

## 2. M0 工程脚手架与环境

**状态：已完成（2026-10-12，Windows 平台实测通过）。** macOS 脚本（`scripts/setup.sh`）已按同等逻辑编写，尚未在 macOS 验证，作为后续扩展任务。

遗留一项：N2.2「新增依赖完整流程」尚未实际演练（当前没有真实的新增依赖需求），首次新增依赖时必须按该流程执行并留档。

**目标**：建立规范与可复现环境，避免 M3 返工。

### 任务

1. 初始化 Git 仓库：固化目录结构（含 `.gitignore`、`.gitattributes`、`.gitkeep`），明确 `Tmp` / `Log` 规则；创建 GitHub 远端（验证阶段设为私有），完成首次推送（按 `30` N8.6、N8.8）；
2. 建立 `pyproject.toml`（Python >= 3.13、ruff、mypy、pytest 配置）与 `uv.lock`，并导出 `requirements*.txt`；
3. 编写 `scripts/setup.ps1` 与 `scripts/setup.sh`，含外部工具检测；
4. 实现 CLI 骨架与 `doctor` 命令（Python 版本、依赖、外部工具、目录可写性）；
5. 建立日志模块（写 `Log/`、按天轮转、`run_id` 串联）与错误码表；
6. 建立 lint/test 本地执行方式，并作为提交前自检项落地（N8.5）；
7. 编写 `README.md`（快速上手指引，指向 `Doc/00`），`LICENSE` 已选定 MIT；
8. 在 `Doc` 中登记首版依赖清单。

### 验收标准（DoD）

- Windows 从零执行 setup 脚本可完成（已验证）；macOS 脚本待后续在真机验证；
- `lpconv doctor` 在两平台均输出完整报告且无 ERROR；
- `Log/` 有日志、`Tmp/` 按 `run_id` 隔离；
- 新增一个依赖的完整流程（N2.2）被实际演练一次并文档化；
- Git 仓库已推送 GitHub（验证阶段私有），`.gitignore` 生效验证通过：`.venv`、`Tmp/*`、`Log/*`、样本均未被跟踪，`uv.lock`、`requirements*.txt`、`Doc/evidence/` 已入库；`README.md` 就位。

### 风险

- Windows 执行策略、PATH、大小写问题（提前按 N3.7/N1.5 约束）。

## 3. M1 设备环境调试

**状态：进行中。** hdc 3.2.0f 已安装并加入 PATH，鸿蒙设备已授权（`Connected`）；iOS 侧 Apple Mobile Device Service 已就绪，回灌通道尚未验证；ffmpeg / ffprobe / exiftool 待安装。

**目标**：把项目最大的两个不确定性（鸿蒙导出、iOS 回灌）解决掉。

### 任务

1. 鸿蒙侧：开发者模式已开启，确认 hdc 连接与文件拉取可用，并校验拿到的是**原始**文件（与设备侧 hash 一致、未被二次转码或剥离）；
2. 确认鸿蒙动态照片在系统中的存在形态（单文件容器 / 双文件 / 媒体库 API 导出），建立机型与系统版本矩阵；
3. iOS 侧回灌通道前期攻坚，**按"先通道、后配对"两步拆解**：
   - 3a. **静态图先行**：先用一张普通静态图验证"外部文件 → iOS 相册"的通道本身是否可用，按优先级依次实测纯 Python + 命令行工具方案（macOS 照片同步、iCloud、第三方命令行工具、快捷指令），每条记录实测结论；
   - 3b. **配对验证**：通道打通后，再用"静态图 + 视频"文件对验证能否被识别为 Live Photo；
   - 仅当上述全部不可行时，才进入"最小 iOS 宿主 App（PhotoKit 写入配对资源）"方案，按 N1.7 评审、N1.8 标记；
4. 建设样本集：不少于 10 组，覆盖横竖屏、不同分辨率、不同时长、HDR/非 HDR、前置/后置；
5. 建立样本登记表（机型、系统版本、来源、hash、时长、分辨率、方向），指纹与登记表入 `Doc/evidence/`，样本本体留 `Tmp/samples/`；
6. 归档每条结论的证据（命令、工具版本、输出）。

### 验收标准（DoD）

- 鸿蒙侧 hdc 拉取连续成功 3 次，产物与设备侧内容一致（hash 校验）；
- iOS 侧**静态图导入**连续成功 3 次（通道可用），**动态照片配对导入**至少成功 1 次且长按可播放；
- 样本集覆盖矩阵达成，登记表完整；
- 产出《M1 设备环境调试报告》（放 `Doc/`），含通道可用性结论、限制与已知问题。

### 风险

- 鸿蒙侧 hdc 拿不到原始文件（A2）：校验 hash，必要时改用图库导出/手动导出兜底输入；
- iOS 回灌通道不可行（R1）：先穷尽纯 Python 通道并归档失败证据；确认无解后按 `30` N1.7 进入"最小 iOS 宿主 App"方案评审，评审通过前不投入后续任务。

## 4. M2 技术方案探索验证

**目标**：以最小成本证明端到端可行，并固化参数与约束。

### 任务

1. 鸿蒙侧解析 Spike：拆出静态帧与动态视频，记录容器结构与关键偏移/字段；
2. iOS 目标格式验证：以 iOS 原生实况照片导出件为参照，确认关联机制、静止帧时刻标记、必需元数据与可行写入工具；
3. 转码参数矩阵验证：编码（h264/hevc）、容器、分辨率、帧率、时长上限、方向处理，逐项记录 iOS 是否接受；**并在前期完成 Q4 兼容情况确认**（超长、超分辨率、编码不兼容时的实际行为）；
4. 端到端 Spike：1~2 组样本走完整链路，产出 iOS 文件对；
5. 真机验证：导入 iOS，确认长按可播放、静止帧与源一致、时长与方向正确；
6. 形成降级策略默认值与限制清单（结论已定：默认截断并在报告显式标注，提供可选策略参数）；
7. 完成 `60-平台格式调研.md` 的结论回填与证据归档；
8. **HDR 与景深兼容性验证（前期完成）**：确认 HDR（GainMap / 色彩空间）在鸿蒙侧可读、iOS 侧可写并保留；景深数据探索可转换性，不可转换则给出明确降级方案。

### 验收标准（DoD / Go-No-Go）

- **Go**：至少 1 组样本在 iOS 真机验证通过（长按可播放、静止帧正确、时长方向正确），且该路径可复现；
- **No-Go**：iOS 回灌或配对机制无法在合理成本内解决 —— 此时应调整技术路线（如引入 iOS 宿主 App、改为 macOS 同步链路）并重新评估范围，而不是继续工程化；
- 参数矩阵表完成（每项标注"接受/不接受/有条件接受"），且**兼容情况结论已在前期产出**（Q4）；
- HDR 结论明确（可保留 / 降级及降级方式），景深结论明确（可转换 / 不可转换并降级）；
- 产出《技术方案验证报告》与《格式调研结论》。

### 风险

- 容器格式未公开且机型差异大（R3）：采用样本驱动逆向 + 可插拔探测设计；
- 工具写入能力不足（A4）：准备备选工具与手写字节方案。

## 5. M3 首个 Converter 实施

**目标**：把验证过的路径产品化。

### 任务

1. 按 `20-架构设计.md` 落地分层：core（IR/注册表/Pipeline/错误码）、platforms（harmonyos/ios）、media 封装、device bridge；
2. 实现 `convert` / `probe` / `verify` / `doctor` 命令；
3. 批量转换：失败隔离、结果报告（人读 + JSON），并探究**并发与断点续做**（任务清单持久化到 `Tmp/<run_id>/`，支持中断后从已完成项继续，见 `30` N6.6）；
4. `verify` 实现：回读产物，校验配对标识一致、时长/编码/分辨率符合 Profile、静止帧时刻正确；
5. 测试：单测 + 集成 + 样本回归（缺样本自动跳过）；
6. 编写《使用说明》并纳入 `Doc`；
7. 真机验收：在样本集上跑全量，统计通过率与失败原因。

### 验收标准（DoD）

- 样本集全量转换，通过率达到目标值（建议先定 ≥90%，失败项均有明确错误码与说明）；
- 每张转换结果都有可追溯的日志与报告条目，降级项被显式记录；
- `verify` 能识别出人为构造的坏样本（配对标识不一致、超长、错误方向）；
- Windows 与 macOS 双平台均可完成一次完整批量转换；
- 批量中断后可续做：中途终止后再次执行，已完成条目不重复处理；并发度可配置且默认保守；
- 使用说明齐备，第三方可按文档自行跑通。
