# LivePhotoConverter 项目总览

> 状态：立项准备阶段（尚未编写业务代码，本文档用于需求评估与立项决策）
> 最后更新：2026-10-12

## 1. 项目背景与目标

各移动平台都实现了「动态照片」（拍一张静态图，同时录一小段视频），但实现互不兼容：

- iOS: Live Photo（实况照片），静态图 + 配对短视频，依靠 Content Identifier 关联；
- HarmonyOS / 华为：动态照片（图库内可长按播放）；
- Android（AOSP 与各家 ROM）：Motion Photo / 动态照片，实现差异大（三星、小米、vivo OriginOS 各不相同）。

结果是跨平台分享（换机、社交传输）后动态效果普遍丢失。**本项目目标**是提供一套可工程化的转换工具链，实现上述平台动态照片的互转。

考虑到完整互转（n×n）的复杂度，项目采用渐进路线：

- 第一期：**HarmonyOS（鸿蒙 7）→ iOS**；
- 后续逐步补齐 iOS→HarmonyOS、Android/OriginOS→iOS 等方向；
- 通过统一中间模型（IR）中转，把 n×n 的实现量降为 n 个「解析器」+ n 个「生成器」。

## 2. 范围界定

### 2.1 本期（M1~M3）范围内

- 鸿蒙侧动态照片的获取与解析（拆出静态帧 + 动态视频）；
- 转换为符合 iOS Live Photo 要求的文件对（静态图 + 配对视频 + 关联元数据）；
- iOS 侧的导入/回灌通道打通与真机验证；
- 命令行工具（批量转换、日志、结果校验）；
- 样本集建设与回归验证。

### 2.2 本期明确不做

- GUI / 移动端 App（除非 iOS 回灌被证明必须依赖宿主 App，届时单独评审）；
- 云同步、账号、社交分享链路；
- 视频剪辑、特效编辑、AI 补帧等增强功能；
- 非动态照片的普通图片/视频处理；
- Android / OriginOS 方向的转换（后续里程碑）。

### 2.3 范围外但需预留

- 播放效果（循环、来回、长曝光）与景深/人像信息；
- HDR / 色彩空间（Display P3、GainMap）的保真；
- 批量规模与并发性能。

## 3. 术语表

| 术语 | 含义 |
| --- | --- |
| 动态照片 / Live Photo | 统称。静态图 + 一小段视频的组合形态 |
| 静态帧（still） | 动态照片中的那张静态图片（JPEG / HEIC） |
| 动态视频（paired video） | 与静态帧配对的那段短视频（MP4 / MOV） |
| 关联标识（Content Identifier） | iOS 用于把静态图与视频配对成 Live Photo 的标识符 |
| 静止帧时刻（still time） | 视频时间轴上对应静态帧的位置 |
| IR（Intermediate Representation） | 本项目定义的平台无关中间模型，转换的中转层 |
| Extractor | 把某平台格式解析为 IR 的适配器 |
| Writer | 把 IR 序列化为某平台目标格式的适配器 |
| Converter | Extractor + 可选变换 + Writer 的组合，即一次点对点转换 |
| Profile（平台约束） | 某平台对动态照片的约束集合（时长上限、允许编码/容器/分辨率、必需元数据），供兼容化变换使用 |
| Device Bridge | 与真机交互的接入层（hdc / adb / MTP / 系统相册同步等） |

各平台官方命名对照：iOS 称 Live Photo（实况照片）；鸿蒙/华为称动态照片；AOSP 称 Motion Photo / Microvideo；vivo OriginOS 为自研实现。

## 4. 总体技术路线

```
[鸿蒙设备/文件] --Extractor--> [IR] --(按 iOS Profile 兼容化)--> [IR'] --Writer--> [iOS 可导入文件对] --> [iOS 相册]
```

- **中转层**：平台无关的 IR 作为唯一中转；iOS 的平台约束固化为 `Profile`，只用于兼容化变换，不参与跨平台语义（已确认）；
- **技术栈**：Python 3.13+，环境管理优先 uv（venv 作为备选），依赖以 `pyproject.toml` + `uv.lock` 为单一真源，`requirements*.txt` 为导出产物（已确认）；
- **跨平台**：提供 Windows（PowerShell）与 macOS（Shell）setup 脚本（放顶层 `scripts/`）；新增依赖必须同步维护脚本与文档；
- **媒体处理**：优先复用成熟命令行工具（ffmpeg/ffprobe、exiftool）而非自研编解码，通过统一封装层调用；
- **设备接入**：优先纯 Python + 命令行工具实现；仅当所有纯 Python 通道均不可行时，才允许单点引入最小非 Python 组件，且须单独评审（已确认）；
- **验证优先**：转换是否成功以真机（iOS 相册长按可播放、静止帧正确）为最终判据。

## 5. 仓库目录结构

```
LivePhotoConverter/
├── Doc/         技术规范、调研与验证报告、开发须知（本文档所在目录）
│   └── evidence/  调研与验证证据（工具输出、元数据快照、样本登记表与指纹）
├── Src/         源码（Python 包、测试）
├── scripts/     环境初始化与工程辅助脚本（setup.ps1 / setup.sh），非业务代码
├── Tmp/         临时文件，按 run_id 分子目录（可随时清理，不入版本库）
│   └── samples/   样本本体（大文件，不入版本库）
└── Log/         运行日志（不入版本库）
```

根目录文件：

| 文件 | 说明 | 是否入库 |
| --- | --- | --- |
| `pyproject.toml` / `uv.lock` | 依赖单一真源与锁定文件 | 入库 |
| `requirements.txt` / `requirements-dev.txt` | uv 导出产物，供 pip 用户 | 入库 |
| `.gitignore` | 排除 `.venv`、`Tmp/*`、`Log/*`、样本、缓存 | 入库 |
| `.gitattributes` | 统一换行（LF）与二进制识别 | 入库 |
| `README.md` | 项目简介与快速上手（指向 `Doc/00`） | 入库 |
| `LICENSE` | 开源协议（公开仓库必需，协议待定） | 入库 |

版本管理使用 Git，远端为 GitHub，规范见 `30` 第 8 节。

目录取舍说明：

- `scripts/` 独立于 `Src`：环境脚本不属于交付包内容，混在源码中会被打包且职责不清；
- `Doc/evidence/` 与样本分离：样本本体（大且敏感）留 `Tmp/samples/` 且不入库，只有登记表与指纹随代码入库，保证证据可追溯又不污染仓库。

## 6. 里程碑总览

| 编号 | 名称 | 核心产出 | 判定 |
| --- | --- | --- | --- |
| M0（建议新增） | 工程脚手架与环境 | 仓库结构、依赖与环境脚本、CLI 骨架、日志、lint | 两台机器上 setup 脚本一键跑通 |
| M1 | 设备环境调试 | 鸿蒙导出通道、iOS 回灌通道、样本集与样本登记表 | 能稳定拿到源样本，且能把产物导入 iOS 相册 |
| M2 | 技术方案探索验证 | 格式调研结论、转码参数矩阵、端到端 Spike | Go / No-Go：至少 1 组样本在 iOS 真机验证通过 |
| M3 | 首个 Converter 实施 | Harmony→iOS 完整 Converter + CLI + 回归测试 | 样本集通过率达标，真机验收通过 |

> M2 是关键决策点：若 iOS 回灌通道被证明不可行，需在此处调整技术路线（例如引入 iOS 宿主 App、改用 macOS 同步链路），而不是继续投入工程化。

各里程碑的任务拆解与验收标准见 `50-里程碑计划.md`。

## 8. 当前状态与下一步

当前处于立项准备阶段。已确认的四项关键决策：

1. **中转层**：IR 为唯一中转，iOS 约束固化为 `Profile`，只用于兼容化变换；
2. **iOS 回灌**：优先纯 Python + 命令行工具，全部不可行时才允许单点引入最小非 Python 组件（须单独评审）；

4. **依赖**：`pyproject.toml` + `uv.lock` 为单一真源，`requirements*.txt` 为导出产物。

下一步建议：

1. 确认剩余待定问题（`10` 中 Q1、Q3~Q8、Q10、Q12），其中 Q1（鸿蒙侧输入形态）与 Q4（降级策略）会直接影响 M1 与 M3 的设计；
2. 进入 M0：搭建工程脚手架、双平台 setup 脚本、`doctor` 命令与日志体系；
3. M1 优先攻克风险最高的两项：鸿蒙侧导出通道、iOS 侧回灌通道。
